# ログインと役割ごとの権限（認証・認可）を足すか

- 状態：**決定**（11/9、Cさん）：提出までにログイン（認証・認可）と個人の受け持ちの割り振りは作らない。今の合言葉のまま。依頼には職種のラベル（`role`）だけを付ける（A-13）。ログイン・受け持ちの割り振り・「誰が確定したか」の記録は、説明ドキュメントとプレゼン動画で「今後の拡張」として書く。理由：画面の作業が増える、明日の凍結までに確かめきれない、受け持ちの考え方を現場に確かめられていない、審査の見せ場（根拠の照合・二段目の確認・人が確定）には効かない
- **追記（11/9）**：ログインは作らないまま、**タスクの担当の割り振りだけ**を足した（[rules.md](rules.md) S-08）。現場の看護師の声「基本の受け持ちは決まっているが、その日の担当は変わることもある。担当外の患者さんからの依頼は、状況によって担当に頼むか、自分で対応している」を受けて。架空の看護師の一覧（`GET /api/nurses`）、患者の基本の受け持ち（seed から入れる）、タスクの担当（作ったときに受け持ちを写し、「担当に回す」「自分で引き取る」で変える）、「自分の担当だけ」の表示。「自分」は画面で選んで `sessionStorage` に置くだけ。下の「ログインがないことによる限界」も参照
- 決めること：提出（11/10 19:00）までにログインと権限を足すか。足すならどの方式・どの範囲を、いつ作るか
- この文書は案。[rules.md](rules.md)・[data-model.md](data-model.md) は変えていない。決まったら両方に写し、変更履歴に書く
- 料金・制限は 11/8 に公式ページで確かめた分だけを書いた（末尾の「確かめた資料」）。確かめられなかったことは **【未確認】** と書いた

## 0. 結論（先に）

- **提出までに Identity Platform のログインは作らない**ことを勧める。作るなら提出の後（本番の構想として資料に書く）
- **提出前に足すなら、「合言葉のまま、最初に看護師を名簿から選ぶ」（3章の案 C）だけ**。それも **音声の検証が片づき、Bさんの画面が最小版の流れを通した後**で、11/9 20:00 の機能の締めに間に合う場合に限る
- 理由：審査の URL では、ログインの情報も提出資料で公開する前提なので、**守りの強さは今の合言葉と変わらない**。得られるのは「誰が確定したか」を記録に残す見せ方と、受け持ちの割り振りの見せ方だけ。一方で、提出後に人が直せない止まり方（パスワードを変えられて審査員が入れない、など）が増える。[日程](../schedule.md) の「削る順番」でも、割り振りは最初に削るもの（0番）になっている

### ログインがないことによる限界（11/9 に担当の割り振りを足したときに書いた）

- **誰が変えたか・確定したかは、自己申告でだけ残す**（11/9 に決めた落としどころ）。画面で選んだ「自分」を `reported_by` で送り、タスク・名簿・記録に `*_reported_by` として残す。本人の確かめはないので「誰がやったと言っているか」までで、証拠にはならない。「自分」を選んでいなければ空
- 「自分」は画面で選ぶだけで、本人かどうかは確かめない。合言葉を知っていれば、誰でも誰の担当でも変えられる（審査の環境は合言葉を公開するので、審査員どうしで担当が変わりうる）
- 受け持ち（`patients.assigned_to`）も、ログインなしで誰でも画面から変えられる（`PATCH /api/patients/{id}`）。6章の「`seed_patients` が起動のたびに `assigned_to` を上書きする」問題は直した（画面で変えた値は残す）
- 本番では、病院の認証で「自分」を決め、受け持ち表は電子カルテと連携し、担当を変えた人を記録に残す（今後の拡張として資料に書く）

## 1. 目的と、作らない場合との比べ

| | 作る（ログイン＋役割） | 作らない（今の合言葉だけ） |
|---|---|---|
| 「誰が確定したか」 | 記録に `confirmed_by`（確定した看護師）が残る。**AI の下書きを、どの人が確かめて確定したか**の証拠になり、テーマ "Own the Why" の説明が強くなる | 記録には「看護師が確定した」ことしか残らない（`patient_check.confirmed_by_nurse` は「確認した」の印で、人は区別しない） |
| 取り違えの防止 | 受け持ちの患者だけを見せる・上に出すと、名簿の隣の行を押す誤り（S-05 の背景）が減る**見込み**（測っていない） | 病棟の全員から選ぶ。誤りは患者の照合（S-02〜S-04）と、名前を大きく出すこと（S-05）で止める |
| 役割の見せ方 | リーダーが受け持ちを割り振る流れを見せられる（S-08 の「余力があれば」） | 割り振りはない。資料に「本番は電子カルテの受け持ち表と連携」と書く |
| 画面の作業（Bさん） | ログインの画面、ログアウト、トークンの取り直しと送り直し、割り振りの画面、401・403 の表示が増える | 増えない |
| 審査員の手間 | ID とパスワードを入れる（合言葉より1項目多い）。役割ごとに入り直す | 合言葉を1回入れるだけ |
| 提出後に止まる原因 | 増える（4章）。11/14 まで人が直せない | 今のまま |
| 守りの強さ | **変わらない**。提出資料に ID とパスワードを書く以上、誰でも入れる。費用の歯止めは今と同じく1日の上限（C-04）と最大1台（C-01） | 同じ |

**大事な点**：審査の環境では「ログイン＝認証」ではあっても、ID が公開されているので「本人である証拠」にはならない。`confirmed_by` は「このアカウントで確定した」までしか言えない。資料にもそう書く必要がある。

## 2. 役割と権限

役割は2つ。リーダーは看護師のできることを全部できる（リーダーも患者を受け持つため）。

| API | 看護師 | リーダー（管理者） | 備考 |
|---|---|---|---|
| `GET /api/patients` 名簿 | ○（見せ方は下の案 X・Y） | ○ 病棟の全員 | |
| `POST /api/drafts`・`POST /api/verify` 下書き・照合 | ○（案 Y なら受け持ちだけ） | ○ | |
| `POST /api/records` 確定 | ○（案 Y なら受け持ちだけ）。`confirmed_by` に自分が入る | ○ | |
| `GET /api/tasks`・`PATCH /api/tasks/{id}` タスク | ○（案 Y なら受け持ちだけ） | ○ 病棟の全員 | `PATCH` したら `done_by`（または `urgency_set_by_nurse`）に自分が入る |
| `PUT /api/patients/{id}/assignment` 割り振り（新規） | ×（`403`） | ○ | |
| `GET /api/nurses` 看護師の一覧（新規） | ×（`403`）か ○（名前だけ）【未決】 | ○ | 割り振りの画面で使う |
| `GET /api/me` 自分（新規） | ○ | ○ | 画面の隅に名前と役割を出すため |

### 看護師に何を見せるか：案 X（病棟の全員）と案 Y（受け持ちだけ）

今は `patients.assigned_to`・`tasks.assigned_to` が常に `null`（[data-model.md](data-model.md) 4章）。

| | 案 X：病棟の全員を見せ、受け持ちに印を付けて上に出す | 案 Y：受け持ちの患者とタスクだけを見せる |
|---|---|---|
| 取り違えの防止 | 隣の行を押す誤りは残るが、自分の受け持ちが上にまとまる | 選べる患者が減るので、誤りの機会そのものが減る |
| 割り振られていないとき | そのまま全員から選べる | **何も見えない**。リーダーが割り振るまで使えない |
| 審査員 | 看護師のアカウントだけで一通り試せる | 先にリーダーで割り振らないと、看護師では空の画面になる。誰かが割り振りを外すと、他の審査員の画面も空になる（アカウントを共有するため。4章） |
| 代わりに対応する場面（休憩中の代行など） | できる | 受け持ちを付け替えるまでできない。現場で代行がどのくらいあるかは**ヒアリングで聞いていない** |
| 決まりの置き場所 | 並べ方は F でよい（安全はこれまでどおり照合で B が守る） | 「受け持ち以外は扱えない」を **B で 403 にする**必要がある（rules.md の「F だけで守らせる決まりは作らない」） |
| 作る量 | 少ない | 多い（全 API で受け持ちを確かめる・テスト） |

**勧め：案 X**。案 Y は審査の環境で空の画面になる止まり方があり、提出後に直せない。

## 3. 認証の方式の比べ

| | 案 A：Identity Platform（Firebase Authentication） | 案 B：自前（Firestore に看護師とパスワードのハッシュ、署名つきのセッション） | 案 C：合言葉のまま、看護師を名簿から選ぶ（認証ではない） |
|---|---|---|---|
| しくみ | 画面が Firebase の JS SDK でメールとパスワードでログインし、ID トークン（**1時間で切れる**）を `Authorization: Bearer` で送る。SDK がリフレッシュトークンで自動で取り直す。バックエンドは Google の公開鍵で検証する（`google-auth` の `id_token.verify_firebase_token`。今の依存に入っている。**鍵ファイルは要らない**、SEC-03） | `POST /api/login` で ID とパスワードを受け、`hashlib.scrypt` で照合し、HMAC の署名つきのセッション（今の二段目の署名 `entail_seals` と同じ作り）を返す | 合言葉を入れた後に「あなたは誰ですか」で看護師を1人選ぶ。画面はその id をヘッダー（例 `X-Nurse-Id`）に付ける |
| 本人の確かめ | する（ただし審査ではアカウントが公開） | する（同上） | **しない**（自己申告）。記録には「自己申告」と残す |
| バックエンドの作業（見積もり、**仮置き**） | 4〜6時間：検証、`Operator` に id と役割、`nurses` の名簿、割り振りの API、`confirmed_by`、テスト | 6〜8時間：上に加えて、パスワードのハッシュ、セッションの署名と期限、ログインの回数制限（メモリで数える）、テスト。**作る量が一番多く、穴を作りやすい** | 2〜3時間：`X-Nurse-Id` を名簿で確かめる、`confirmed_by`、割り振りの API（作るなら）、テスト |
| 画面の作業（Bさん、見積もり、**仮置き**） | 4〜6時間：SDK の読み込みと初期化、ログイン・ログアウトの画面、すべての呼び出しにトークンを付ける、401 で取り直して1回だけ送り直す、割り振りの画面 | 3〜5時間：ログイン・ログアウトの画面、セッションを付ける、401 でログインに戻す、割り振りの画面 | 1〜2時間：看護師を選ぶ画面（合言葉の入力の次）、画面の隅に名前、割り振りの画面（作るなら＋2時間） |
| GCP の設定 | Identity Platform を有効にする、メールとパスワードのログインを有効にする、デモ用のアカウントを作る、承認済みドメインに Cloud Run の URL を入れるか【未確認：メールとパスワードのログインだけで要るか】 | `nurses` に看護師とハッシュを入れる。セッションの署名の鍵を環境変数で固定する（今の `ENTAIL_SEAL_KEY` と同じく、無いと起動のたびに作り直され、再起動で全員がログアウトになる） | 増えない |
| 費用 | メールなど Tier 1 は **月 50,000 MAU まで無料**（Identity Platform の料金表）。審査で使うのは数人なので無料枠に収まる見込み。Firebase の料金表でも Spark で 50K MAU。電話（SMS）は使わない | 増えない（Firestore の読み書きが少し増えるだけ） | 増えない |
| 提出後に止まる原因 | ①**公開したアカウントのパスワードを誰かが変える**と、他の審査員が入れなくなり、11/14 まで戻せない（Firebase はパスワードの変更で既存のトークンも無効にする）。画面に変更の機能を作らなくても、公開の Web API キーと ID トークンがあれば REST で変えられる**見込み**【未確認：プロジェクトの設定で止められるか】②パスワードを何度も間違えると一時的に止まる場合がある【未確認：回数と時間は公式の制限の表に無い】③SDK を外部（`gstatic.com` など）から読むなら、その配信に頼る④Identity Platform 自体の障害 | ①ログインの回数制限で、公開のアカウントを誰かがわざと間違え続けると締め出される（制限を IP ごとにすれば緩む。C-04 と同じく `X-Forwarded-For` は書き換えられる）②署名の鍵を固定し忘れると、再起動のたびに全員がログアウト | ほぼ増えない。名簿にない id は `403` |
| 審査員の使いやすさ | 合言葉の代わりに ID とパスワード。役割を見るには入り直す | 同じ | 合言葉＋1タップ。役割の切り替えは選び直すだけ |
| 審査での見え方 | Google の認証の製品を使っている（Google 技術の利用として説明できる**かもしれない**。審査基準で加点になるかは [審査基準との対応](../submission/judging-map.md) で確かめていない） | 自作の認証は「なぜ既製品を使わないか」を問われうる | 「本番は病院の認証（SSO）と連携し、ここは自己申告」と書けば筋は通る |

### SEC-03・SEC-02 との食い違い（案 A）

- Firebase の JS SDK は、画面に **Web API キー**（`apiKey`）を含む設定を置く。この値は秘密ではない（プロジェクトを指す識別子）が、SEC-03 の「API キーは使わない」と文面で食い違う。SEC-03 を「GCP の**サービスを呼ぶ**認証にキーを使わない。Firebase の Web 用の設定は例外」と直す必要がある
- [data-model.md](data-model.md) 1章は「画面に Firebase の設定や認証を持たずに済む」を、画面を Firestore につながない理由に挙げている。案 A では画面が Firebase（認証）に直接つながる。**Firestore には今までどおりつながない**（SEC-02 は変わらない）が、理由の書き方は直す

## 4. 審査員のログイン

| 項目 | 案 A・B | 案 C |
|---|---|---|
| 渡し方 | 提出資料に **看護師用とリーダー用のデモのアカウント**（ID とパスワード）を書く。公開前提。**公開されても困らない値**にし、他で使っているパスワードは使わない。合言葉は残すか（6章の `AUTH_MODE`）次第 | 合言葉は今のまま資料に書く。看護師は名簿から選ぶ |
| パスワードを忘れた | 資料を見直してもらう。パスワードの再設定のメールは、デモのアカウントの宛先を誰も受け取れないので**使えない**（受け取れる宛先にすると、そのメールを持つ人しか直せない） | 起きない |
| 締め出された・止まった | 案 A は【未確認】の一時的な止まり、案 B は自前の回数制限。**11/14 まで人が解除できない**。予備のアカウントを資料に2組書く案がある（どれか1つが止まっても入れる） | 起きない |
| アカウントを共有した場合 | 全員が同じ人として記録される（`confirmed_by` で審査員を区別できない）。案 Y なら1人の割り振りの変更が全員に効く。案 A では1人がパスワードを変えると全員が止まる（3章 ①） | 同じ看護師を選べば同じ。選び直しはいつでもできる |

## 5. API の変わる所（案）

[data-model.md](data-model.md) の形に合わせた案。決まったら data-model.md に写し、変更履歴に書く。

### ヘッダーと 401・403

| 設定 `AUTH_MODE` | 受けるもの | 操作した人 |
|---|---|---|
| `passcode`（既定。今と同じ） | `X-Passcode`。案 C を足すなら、加えて `X-Nurse-Id`（任意） | `X-Nurse-Id` があれば、その看護師（自己申告）。なければ不明 |
| `identity`（案 A） | `Authorization: Bearer <ID トークン>`。`X-Passcode` は見ない | トークンの看護師 |

- **移行の間に両方を受ける形（どちらかが合えば通す）は作らない**ことを勧める。両方を受けると、合言葉で入った人は誰か分からず、`confirmed_by` が空の記録が混ざる。手元の開発では `passcode` のまま、試すときだけ `identity` にする
- 提出のときにどちらかに決め、提出後は変えない（設定の変更は禁止のため）

エラー（形は今の `{"mode", "error": {"code", "message"}}`）：

| 状態 | code | いつ | 画面 |
|---|---|---|---|
| 401 | `bad_passcode` | 合言葉が違う（今と同じ） | 合言葉の入力に戻す |
| 401 | `no_token` | `identity` で `Authorization` が無い | ログインに戻す |
| 401 | `invalid_token` | トークンが不正・期限切れ | SDK でトークンを取り直して**1回だけ**送り直す。駄目ならログインに戻す |
| 403 | `unknown_nurse` | トークンは正しいが `nurses` にいない／`X-Nurse-Id` が名簿にない | 「この画面を使えるアカウントではありません」 |
| 403 | `forbidden_role` | 看護師が割り振りの API を呼んだ | 割り振りの画面を出さない（それでも B で止める） |
| 403 | `not_assigned` | 案 Y のときだけ：受け持ちでない患者・タスク | 名簿に戻す |

### 新しく足すもの

```json
// GET /api/me
{"mode": "live", "nurse": {"id": "n01", "name": "看護師A", "role": "nurse", "auth": "identity"}}

// PUT /api/patients/{id}/assignment（リーダーだけ）
{"nurse_id": "n01"}            // 外すときは null
// 出力：名簿の1件と同じ形（assigned_to が入る）
{"mode": "live", "patient": {"id": "p302", "room": "302", "...": "...", "assigned_to": "n01"}}
```

- `role` は `nurse` か `leader`。`auth` は `identity`（ログインした）／`self_declared`（案 C の自己申告）
- 存在しない看護師・患者は `404`（`nurse_not_found`・`patient_not_found`）

### 記録とタスク

| どこ | 足すもの | 中身 |
|---|---|---|
| `records/{id}` | `confirmed_by` | `{"nurse_id": "n01", "name": "看護師A", "auth": "identity"}`。合言葉だけで誰か分からないときは `null`。名前は確定のときの写し（後で名簿が変わっても残す） |
| `POST /api/records` の出力 | `confirmed_by` | 同じ。画面の確定の後に「看護師A が確定」と出せる |
| `chart_text` | 変えない | カルテには、カルテ側のログインで記録者が残る想定。【未決】先頭に記録者を入れるか（R-01 の順が変わる） |
| `tasks/{id}` | `assigned_to` | 確定のときに、その患者の `assigned_to` を写す（割り振りが無ければ `null`）。確定した人ではなく受け持ちの人に付ける案。【未決】どちらに付けるか |
| `tasks/{id}` | `done_by` | `PATCH` で済みにした看護師の id |
| `GET /api/tasks` | `?mine=true` | 自分の受け持ちのタスクだけ（案 X でも絞り込みとして使える） |
| `nurses/{id}`（新しいコレクション） | `name`, `role`, `ward` | 架空のデモの看護師。起動時に `backend/seed/nurses.json` から入れる。案 A の id は Identity Platform のユーザーの uid にする。案 B はここにパスワードのハッシュも入る。患者の情報ではないので TTL は付けない |

役割を Identity Platform の **custom claims** に持たせる方法もあるが、管理の SDK で設定する手間が増え、変えてもトークンの取り直しまで効かない。`nurses` に持つ方が、バックエンドだけで完結する。

## 6. バックエンドの土台

今は [`backend/app/auth.py`](../../backend/app/auth.py) の `authenticate` が合言葉だけを確かめ、`Operator(nurse_id=None)` を返す。`main.py` が全ルートに `dependencies=[Depends(authenticate)]` で付けていて、**ルートの関数は `Operator` を受け取っていない**。

案：`AUTH_MODE=passcode|identity` を設定に足し、既定は `passcode`。`authenticate` の中で切り替える。

| ファイル | 変わること | 見積もり（**仮置き**） |
|---|---|---|
| `app/config.py` | `auth_mode` を足す（`passcode` / `identity` 以外は起動を止める）。`identity` のときは `GOOGLE_CLOUD_PROJECT` をトークンの宛先（audience）として使う | 小 |
| `app/auth.py` | `Operator` に `nurse_id`・`name`・`role`・`auth` を足す。`passcode` は今の確かめ＋`X-Nurse-Id`（案 C）、`identity` は `verify_firebase_token` で検証し `nurses` を引く。`require_leader`（リーダーでなければ 403）を足す | 中 |
| `app/routes/records.py`・`tasks.py` | 引数に `operator: Operator = Depends(authenticate)` を足し、`confirmed_by`・`done_by` を入れる（FastAPI は同じ依存を1回の要求の中で使い回すので、二重に確かめない） | 小 |
| `app/services/confirm.py`・`record_documents.py` | `confirmed_by` を記録に入れる。タスクの `assigned_to` を患者から写す（今は常に `None`） | 小 |

| `app/store/base.py`・`memory.py`・`firestore_store.py` | 割り振りの書き込み、`nurses` の読み込み、`list_tasks` の絞り込み | 中 |
| **`firestore_store.py` の `seed_patients`** | **今は起動のたびに名簿を丸ごと `set` で上書きするので、割り振った `assigned_to` が `null` に戻る**。最小インスタンス数が0なら、しばらく使われないたびに割り振りが消える。`assigned_to` を上書きしない（無い患者だけ入れる、か `merge`）形に直す必要がある | 小（ただし直し忘れると提出後に壊れる） |

| `app/models/api.py`・`record_request.py` | `Me`・`Assignment`・`confirmed_by` の型 | 小 |
| `backend/seed/nurses.json`、`backend/mock/` | デモの看護師、モックの応答に `confirmed_by` | 小 |

| `requirements.txt` | 案 A でも足さなくてよい見込み（`google-auth` が今の依存に入っている）。`firebase-admin` を使うなら足す | — |

### 成果仮説（案 C を足した場合。数値は仮置き）

- 指標：11/9 の通し（3人）で、確定した記録のうち `confirmed_by` が入っている割合と、看護師を選び間違えた回数（自己申告を間違えた回数）
- 続ける：割合 100%、選び間違い0回。直す：選び間違いが1回以上（選ぶ画面を合言葉の直後でなく録音の前に出す、など）。やめる：選ぶ画面で通しの時間が手で書くより長くなる人が増える（[設計](README.md) 1章の指標①を悪くする）なら外す
- 判断：11/9 20:00（機能の締め）
- 計測準備：`POST /api/records` の操作記録（Cloud Logging）に `auth`（`self_declared` か `null`）を足す。名前は出さない（P-04 の案）

## 9. チームで決めること

1. **提出までに作るか**（勧め：音声と最小版が通った後に、案 C だけ。そろわなければ作らない）——Aさん
2. 作るなら方式：案 A・B・C のどれか（勧め：C）——Cさん・Bさん
3. 看護師に見せる範囲：案 X（全員＋受け持ちに印）か案 Y（受け持ちだけ）（勧め：X）——Aさん
4. 割り振りの画面（リーダー）まで作るか、`confirmed_by` だけにするか——Bさんの空きで決める
5. タスクの `assigned_to` を、患者の受け持ちから写すか、確定した人にするか
6. ログに看護師の識別子（`nurse_id`）を出してよいか（P-04）
7. カルテ用の文（`chart_text`）に記録者を入れるか（R-01）
8. 案 A を選ぶ場合：デモのアカウントを何組公開するか、パスワードの変更を止める設定があるかを誰が確かめるか、SEC-03 の文面をどう直すか
9. 提出のときの `AUTH_MODE` を誰が確かめるか（提出後は変えられない）
