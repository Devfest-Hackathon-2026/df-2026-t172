# チームの約束・書き方・承認

人と AI（Kiro・Claude Code など）の両方が守る約束。もとは `.kiro/steering/` の `team.md`・`structure.md`・`cost.md` にあったもので、中身は変えずにここへ移した（2026-11-19、Cさん）。Kiro は `.kiro/steering/project.md` からこの文書を読み込む。

## チームの約束

- 返事・文書・コメント・コミットメッセージの説明は**日本語**。コード・識別子・コマンドは原文のまま
- 結論を先に、詳しい中身は後に書く。「〜と思います」などのあいまいな言い方を避ける。一文が長くなったら分ける
- 人の名前は、Aさん（企画・進行）・Bさん（画面）・Cさん（バックエンド・DB・データ形式、このリポジトリの持ち主）と書く。本名・GitHub のユーザー名・メールアドレスは書かない
- `.env`・鍵・合言葉・トークンは読まない・書かない・出力しない・コミットしない
- commit・push・ブランチの削除・履歴の書き換えは、頼まれたときだけ。コミットメッセージは Conventional Commits（`feat: 説明` など。type は feat / fix / docs / refactor / chore / test）
- ファイルの削除・上書きなど取り消しにくい操作は、先に確かめる
- AI に手伝ってもらったら、`docs/submission/ai-usage-log.md` に1行足す。製品名は書かず「対話型 AI」と書く。**なぜその場面で AI を使ったか**と、**採らなかった提案・人が直したこと**も書く
- 作業を始める前に、目的・終わったと言える条件を短く書いてから進める。大きな作業は、要件・設計・手順の順に人が確かめる（Kiro では Spec を使う）

### バックエンドの書き方

- 型ヒントを必ず付ける。公開関数には Google スタイルの docstring
- `ruff check` と `ruff format`（設定は `backend/pyproject.toml`、行の長さ 100）
- 裸の `except:` は使わない。具体的な例外の型を書く
- 1ファイル1責務。200行を超えたら分けることを考える
- 照合・判定はコードで書き、AI の答えをそのまま信じる書き方をしない
- 画面から届いた値（照合の結果・発言の列）をそのまま信じない。確定の可否はサーバーで照合し直して決める

### 画面の書き方

- 素の JavaScript の ES モジュール。ビルドの仕組みは足さない
- API の呼び出しは `frontend/js/api.js` に集める。画面から Firestore や Google のサービスに直接つながない（SEC-02）
- 読み込むファイルを変えたら、`index.html` の読み込みの版（`?v=...`）を上げる（古いキャッシュで直したものが隠れたことがある）

### テストの書き方

- 決まり（`docs/design/rules.md`）を確かめるテストは、名前に番号を入れる：`test_A05_...`、`test_S03_...`
- 正しい例だけでなく、**わざと壊した例**（誤りが通らないこと）も書く
- 外部のサービスは差し替えて動かす。テストから Gemini・Speech-to-Text・Firestore を本当に呼ばない
- 照合を直したら `python -m scripts.build_mocks` でモックを作り直す（`test_mock_files.py` が古いモックを見つける）

## お金がかかる呼び出しと GCP の設定変更

**実行の前に、必ず承認を取る。** 承認なしで実行しない。テストや確かめのつもりでも同じ。

- 承認する人：11/19 までは Cさん。**11/20 以降は Bさん**（11/19 Cさん決定）
- Bさんが承認してよいのは、Cloud Run のデプロイ・切り替え・戻すことと、決めた上限までの live での確かめだけ。API の有効化・Firestore・Secret Manager・IAM・予算は承認できない（Bさんへの引き継ぎ（非公開の運用メモ） 4章）

### 承認が要るもの

| 種類 | 例 |
|---|---|
| お金がかかる呼び出し | Gemini（Vertex AI）、Speech-to-Text、`MODE=live` のサーバーへの下書きの作成、総合テストの `--allow-paid`、`backend/scripts/run_live_scenarios.py`・`run_live_speech.py` |
| GCP の設定変更 | API の有効化、Cloud Run のデプロイ・設定の更新、Firestore（データベース・TTL・ルール・インデックス）、Secret Manager（値・バージョン・権限）、IAM、予算アラート |

読むだけの確認（`describe`・`list`）は承認なしでよい。ただし秘密情報の値を表示するコマンドは使わない。

gcloud の既定のアカウントはハッカソン用ではない。コマンドには毎回 `--project df-2026-t172` と、ハッカソン用のアカウント（11/20 以降のデプロイは Bさんのアカウント）を付け、既定の設定は書き換えない。

### 費用の出し方

承認を取るときは、次を表で出す。わからない値（録音の長さ・回数など）は推測で埋めず、先に聞く。

1. 使うものの単価（入力・出力・**思考トークン**・音声の分あたり）と無料枠。**公式の料金ページで確かめた日**を書く
2. 1回あたりの入力・出力のトークン数（または音声の長さ）
3. 回数
4. 合計（ドルと円。1ドル＝150円で計算し、幅があれば最小〜最大）

```
| 項目 | 単価 | 数量 | 小計 |
|------|------|------|------|
| 入力トークン | $X/1M | X tokens | $X |
| 出力トークン（思考を含む） | $X/1M | X tokens | $X |
| 音声の文字起こし | $X/分 | X 分 | $X |
| 合計 |  |  | $X（約¥X） |
```

- 2026-11-08 に確かめた単価：`gemini-3.5-flash`（`global`）入力 1.50ドル・出力 9.00ドル（100万トークンあたり。思考トークンは出力の単価）。Speech-to-Text V2 標準 0.016ドル/分（1秒単位）。**使う前に公式ページで見直す**
- 3系の Gemini は思考を完全には止められない。思考トークンを数えて費用に入れる
- 少量で試してから増やす
- 予算は Cloud Credit の20ドル（約3,000円）から始まっている。残りは Cさんに確かめる
