# Spec を作るときの約束

機能ごとに `.kiro/specs/<機能名>/` を作る。機能名は英小文字とハイフン（例 `nurse-login`）。各段階の文書ができたら止まり、**人が確かめてから次の段階に進む**。

## requirements.md（何を満たすか）

- 冒頭に、**なぜ作るか**を書く。根拠（ヒアリング・審査の講評・既存の資料）を示し、根拠がなければ「仮説」と書く
- 要件は「〜のとき、システムは〜する」の形で、確かめられる書き方にする
- **関わる決まりの番号**（`docs/design/rules.md`、例 A-05・P-02）を要件ごとに書く。決まりとぶつかる要件は、ぶつかることを書いて人に決めてもらう
- **作らないこと**も書く（範囲を広げすぎないため）
- 成果を後で確かめる方法（何を記録し、どの結果ならどう判断するか）を書く。数値に根拠がなければ「仮置き」と書く

## design.md（どう作るか）

- 変える API と保存の形を、`docs/design/data-model.md` の書き方に合わせて書く。実装したら data-model.md を直し、変更履歴に1行足す
- 新しい決まりが要るなら、`docs/design/rules.md` の表の形で案を書く（番号・決まり・なぜ・守らせる場所・確かめ方）
- 比べた案と、選んだ理由・捨てた理由を書く。技術を変えるなら ADR の案も書く
- **お金がかかる呼び出しが増えるか**を書く。増えるなら、1回あたりの費用の見込みを `docs/conventions.md` の「費用の出し方」の形で出す
- 個人情報が増えないか（保存するもの・ログに出すもの）を書く

## tasks.md（作業の手順）

- 1つの手順は、テストで確かめられる大きさにする
- テストを先に書く手順を入れる。決まりのテストは名前に番号を入れる。わざと壊した例も書く
- 最後の手順は必ず「バックエンドと画面の全テストを回す」：

```bash
cd backend && .venv/Scripts/python -m pytest -q && .venv/Scripts/ruff check . && .venv/Scripts/ruff format --check .
node --test frontend/tests/*.test.mjs
```

- お金がかかる呼び出し・GCP の設定変更・デプロイの手順には「**Cさんの承認が要る**」と書き、その手順の前で止まる
- `docs/submission/ai-usage-log.md` に1行足す手順を入れる
