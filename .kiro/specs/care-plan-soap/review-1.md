## 指摘

### 1. 重大：看護計画を選ぶと「残す／消す」が外れ、確定できない

**指摘**

確認画面の `ReviewSession` は、「残す／消す」を決めたときに、その文の指紋を一緒に覚える。指紋は、`targetAt(this.draft, path)` が返す文のオブジェクト全体と、その文への指摘を JSON にしたもの。`action(path)` は、今の指紋が覚えた指紋と同じときだけ決定を返す。design のとおり文に `plan_id` を書き込むと指紋が変わり、決定はないものとして扱われる。`gate()` は「残す／消すの選択が1件あります」を出し、確定ボタンが押せなくなる。照合が通ったあとの片づけ（`verify()`）も、指紋の違う決定を消す。

design の「確認画面の振る舞いの要点」は「touch() を通さない」ことだけを書き、「`checks` の `path`、「残す／消す」は変わらない」（D471）と言い切っている。touch() を通さなくても決定は外れる。要件5の7（その文で選んだ「残す／消す」を残す）と5の8（確定ボタンの状態を変えない）を満たせない。

手元で確かめた。`backend/mock/draft_s3.json` から `ReviewSession` を作り、`soap.S[2]` に「消す」を決め、その文に `plan_id` を書き込んだ。`action("soap.S[2]")` は `delete` から `null` に、`gate()` は `ready: true` から `ready: false`（「残す／消すの選択が1件あります」）に変わった。

波及は2つある。決定を作り直すために看護計画の選択で touch() や照合を通す作りにすると、確定ボタンが「修正内容を再検証してください」で止まり、要件5の8 に反する。そこで `entail: true` を送れば、要件7の5（Gemini の回数）も崩す。また、文を置き換える書き方（`soap.S[i] = {...s, plan_id}`）にすると、指紋の問題はそのまま残り、さらに足した文の見分け（`addedElements` は文のオブジェクトで覚える）が外れる。足した文の削除ボタンと根拠の選択が消える。

**根拠**

- `frontend/js/records.js:214-218`（`fingerprint`）、`:234-237`（`action`）、`:370`（`decide`）、`:408-411`（`gate`）、`:452`（`verify()` の片づけ）
- `frontend/js/records.js:288`・`:330`、`frontend/js/components/review-entry.js:86`（足した文はオブジェクトで見分ける）
- design.md D468・D470・D471。画面のテストの表 D1227（5の7・5の8 の行。書いてある作りでは、このテストが落ちる）
- 要件5の7・5の8・7の5
- 確度：確認済み（上の手元の確かめ）

**直し方の案**

- design の「確認画面の振る舞いの要点」に2行足す。(a) 「残す／消す」の指紋から `plan_id` を除く（`fingerprint` で、`targetAt` の結果から `plan_id` を外してから JSON にする）。(b) `plan_id` は今の文のオブジェクトに直接書き、オブジェクトを置き換えない
- 画面のテストの 5の7・5の8 の行を具体的にする。「残す／消すを決めてから看護計画を変えても、`action()` と `gate()` が同じ」「足した文の看護計画を変えても、削除ボタンと根拠の選択が残る」

### 3. 中：R-03 の確かめがルートの1か所にだけあり、機能2の入口ですり抜ける

design は `ensure_known_care_plans` を `routes/records.py` の `create_record` に置き、理由に「`services/confirm.py` を変えずに済む」（D201）を挙げる。しかし同じ design が、確定のログのために confirm.py を変える（D735-757）。理由は成り立っていない。

機能2（仮保存・確定し直し）は、たたき台で confirm.py・`record_status.py`（新規）・store を触る予定。記録を書く入口が増えると、その入口は看護計画の確かめを通らない。今のルートには A-12 の確かめ（`relabel_ai_elements`・`ensure_nurse_evidence_exists`）も並んでいるので、入口を足す人はこの3つを全部写す必要がある。R-03 の「画面の作りに漏れがあっても記録に入らない」は、入口が1つの間しか守られない。

**根拠**

- `backend/app/routes/records.py:53-71`、design.md D197-203・D735-757
- `docs/planning/final-dev-plan.md` 5章の 2c・2e
- 確度：可能性高い。機能2の Spec（2a）で、記録を作る入口が `POST /api/records` だけのままかを確かめる

**直し方の案**

### 4. 中：Firestore の `care_plans` は書くだけで読まれない（要件2の9 と案A）

**指摘**

案A では、名簿API と受け持ちAPI は `with_roster_care_plans` で起動時の名簿の値に置き換える。下書きAPI・確定API・記録閲覧API は、もともと起動時の名簿を使う。Firestore の `patients.care_plans` を応答に使う API は1つもない。それでも要件2の9（決定3）のとおり、起動のたびに Firestore に書く。

書くことで増えるのは次の2つだけ。

- 保存先にある病状に関わる情報（看護計画の名前）。要件9の7 で `records` に label を残さないと決めたのに、`patients` には残す
- 失敗の道。`Patient` の型の条件は Firestore から読むときにもかかる。Firestore の `care_plans` が条件に合わないと、名簿API（全員分）・受け持ちAPI・下書きAPI・確定API（`with_current_assignee` が `get_patient` で読む）が 500 になる。design は「人が手で書き換えない限り起きない」（D1104）とするが、その値はどこでも使われない

design の (c)（D186-191）が `Patient` に足す利点に挙げた「名簿API・下書きAPI の応答を組み立て直すコードが要らない」は、案A の `with_roster_care_plans` でなくなっている。

**根拠**

- design.md D158・D162・D186-191・D825-826・D1104
- `backend/app/store/firestore_store.py:40`（書く）・`:51`・`:58`（読むときに `Patient` で検証する）、`backend/app/routes/deps.py:50-55`
- 要件2の9・9の7、決定3
- 確度：確認済み

**直し方の案**

- 要件2の9 を「Firestore の `patients` に `care_plans` を書かない」に変える。`FirestoreStore.seed_patients` を `exclude={"id", "care_plans"}` にし、読むとき（`list_patients`・`get_patient`・`set_patient_assignee`）は `care_plans` を捨てる。store/ は機能2の担当も触るので、20:00 より前に入れる
- 変えないなら、design の「個人情報」の節に使わない値を保存する理由を書き、要件2の9 の理由を案A に合わせて書き直す

### 5. 中：決定7 で分けた文が、A-12 の照合と二段目の外に出る

**指摘**

決定7 では、1つの文に看護計画の話と計画外の話が混ざったとき、看護師が文を直して分ける。今の画面で分ける手段は「AI の文を直す」と「文を足す」だけで、足した文は `added_by: nurse` になる。画面は、足した文が元の AI の文と全文で同じときだけ `ai` に戻す。サーバーの `draft_token` も文全体の指紋で照らす。AI の文の一部を写した文はどちらにも当たらないので、看護師が足した文として、照合（根拠のない文・数の食い違い・薬の語・話者を止める）と二段目を通らない。

要件7の8 と design の費用の節（D1261）は、直した AI の文を確定のときに1回呼び直すことだけを書き、写した片方の扱いに触れていない。結果として、この機能の手順が、A-12 が防いでいる「AI の文を看護師の文として通す」形をふだんの操作にする。

**根拠**

- 要件7の8・決定7、design.md D1261
- `frontend/js/records.js:301`、`backend/app/services/draft_token.py:46`、`backend/app/checks/verify.py:78`、`backend/app/checks/entail.py:51`
- 確度：確認済み（コードの流れ）。看護師が実際にこう分けるかは、成果の指標②の試しで見る

**直し方の案**

requirements の「わかっていないこと・人に決めてもらうこと」に足して、人が決める。案は2つ。

- (a) 分けた片方は看護師の文として照合の外に出ることを認め、A-12 の「なぜ」に書く
- (b) 画面に「文を分ける」操作を足し、分けた片方を `added_by: "ai"`・元の文と同じ根拠で足す。確定のときの呼び直しは、裏付けのない文をまとめて1回で送る（`backend/app/services/drafting.py:110`）ので、Gemini の回数は増えない。画面の作業は増える

## 一番危ない前提

「`plan_id` を文に足すだけなので、文の場所・署名・draft_token・残す／消すの仕組みは何も変わらない」という前提。

design はこの前提を、印を付ける案を選んだ理由（(a)）と、費用が増えない理由の土台にしている。サーバー側ではコードで確かめてあり、成り立つ。しかし確認画面は「残す／消す」を文の中身ごと覚えていて、`plan_id` もその中身に入るので、画面ではこの前提が成り立たない。画面のコードはまだなく、design の指示だけを持って画面の担当に渡る。気づかずに作ると、看護計画を選んだ「止める」文で確定ボタンが止まり、看護師は選ぶたびに「残す／消す」を選び直すことになる。照合のやり直しで直そうとすれば、確定ボタンが再検証待ちになり、`entail: true` なら、この機能が「増えない」と約束した Gemini の回数も増える。画面に渡す前に、指紋から `plan_id` を除くことを design に書くのが一番安い。
