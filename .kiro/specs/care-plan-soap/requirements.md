# Requirements Document

## Introduction

### 結論

- 患者ごとに看護計画（例 `#急性疼痛`）を名簿に持たせる。確認画面で、看護師が S・O の文ごとに「どの看護計画の文か」を選ぶ。どの計画にも当たらない文は「計画外」の欄にまとめる。カルテ用の文は看護計画ごとにまとめ、計画外の文はその後にまとめる
- 文は `soap.S`・`soap.O` の同じ場所に置いたまま、`plan_id` の印を付けるだけにする。照合・二段目の署名（`entail_seals`）・`draft_token` の仕組みは変えず、Gemini と Speech-to-Text の呼び出しは増えない
- 看護計画は、起動のときに名簿seed から読んでメモリにだけ置き、Firestore（`patients`・`records`）には書かない。記録には文ごとの `plan_id` だけを残し、看護計画の `label` の写しは残さない。記録閲覧API は、起動時の名簿の看護計画からカルテ用の文を作り直す
- 看護計画の `id` は、名簿全体で重ならない、中身の分からない番号（`cp01` など）にする
- AI（Gemini）は文に計画を付けない。患者の看護計画を Gemini に渡すと A-09 とぶつかるため
- R-01（カルテ用の文の順番）の書き換えと、新しい決まり A-14・R-03 は、11/18 に Cさんが決めた。実装のときに `docs/design/rules.md` に写す（「決まりとの関係」の節）。ほかに 11/18 に決めたことは「決めたこと（11/18、Cさん）」の節にまとめた
- 11/18 の1回目の設計レビュー（`review-1.md`）を受けて、決定3（Firestore に書かない）と決定6（id の形）を変え、要件1の2〜1の4・1の9・2の9・4の2・4の4・6の2・7の8・8の15・9の2・9の4・9の7 を直し、要件1の10 を足した（番号は変えていない）。主な所に「review-1 の指摘N」と書いた
- review-1 の指摘5（1つの文を分けたとき）は、11/18 に Cさんが案 (b)（確認画面に「文を分ける」操作を足す）に決めた（決定7）。これに合わせて要件5の15〜5の19・6の10 を足し、要件7の8 を直した
- 11/19 の2回目の設計レビュー（`review-2.md`）を受けて、要件5の20〜5の23（削除予定の文は分けられない、分け目の指定、空の半分、「分けを戻す」）を足し、要件5の11 に削除予定の文の `plan_id` を `null` に戻すことを足した

### なぜ作るか

根拠は、11/18 に看護師1名（チームの友人）に架空の台本でアプリを試してもらった感想（家族が患者役。録音 → 下書きの確認 → 確定まで）。11/18 に Discord で共有され、決勝の追加開発のたたき台（非公開の運用メモ） の1章にまとめた。[ヒアリング記録](../../../docs/research/hearing.md) にはまだ載っていない。

#### 聞いた事実

- 直してほしい点の中で、これが一番大事と言われた
- 記録は看護計画に対して書く。そのため、S には計画に関係する内容だけを入れてほしい
- 例：「#急性疼痛」なら「起き上がるときにズキッとする、10段階で4」が S
- 「お茶がほしい」「夜トイレで起きる」は必要な情報だが、計画とは別なので、別の欄に入れて把握できるといい

#### チームの解釈（事実ではない）

- 看護師は、看護計画（看護上の問題）ごとに SOAP を書いている。今のアプリは S・O を1つの欄にまとめて出すので、看護師が計画ごとに書き分け直す手間が残る（仮説）
- 「別の欄」は、カルテ用の文の中で、看護計画の欄の後に「計画外」の欄としてまとめる形と解釈した。看護師には確かめていない
- 「お茶がほしい」は、今のアプリでも依頼（タスク）として S・O とは別に出る。残る「夜トイレで起きる」のような S・O の文を、計画外の欄に分けることが今回の中心になる
- 文ごとの計画の選択は、看護師が手で選べば足りる（仮説）。AI による自動の仕分けは作らない（「作らないこと」）
- 看護師1名の感想で、病院・病棟が変われば記録の書き方も違う可能性が高い。一般化しない

#### 最小版に絞る理由

- 追加開発の期間は 11/18 12:00〜11/24 23:59。バックエンドの Cさんが使えるのは 11/18 22:00 以降と 11/19 終日だけ
- 最小版のバックエンドの目安は約15時間（仮置き。テストとデプロイを含む）で、Cさんの時間はほぼ一杯になる
- そのため、看護師が文ごとに計画を選ぶ形に絞り、AI の仕分け・計画ごとの A・P・計画の編集画面は作らない

### 台本の場面と、期待する仕分け（受け入れの例）

決勝のデモの台本（305号室 佐藤 和夫さん、架空）の会話が、どこに入るかの期待。新しい台本は live のデモで使う（モックの見本は作り直さない。決定6）。行き先は今のアプリの決まりどおり、看護計画はチームの解釈（305号室の看護計画のうち、台本の文に当たるのが `#急性疼痛`（`cp04`）だけの場合）。

| 会話の内容 | 行き先（今の決まり） | 看護計画（期待） |
|---|---|---|
| 術創は起き上がるときにズキッとする、10段階で4 | S | `#急性疼痛` |
| 夜中に2回トイレで起きて、あまり眠れなかった | S | 計画外 |
| 朝食は半分、食欲がない | S | 計画外 |
| お茶は飲んでいる | S（S に入った場合） | 計画外 |

| 先生に退院の時期を聞いてほしい | 医師への確認 | 付けない |
| 孫の野球の話 | どこにも入れない（雑談） | — |

この場合のカルテ用の文の例（形は R-01 の書き換え。11/18 決定。文の中身は AI の下書きと看護師の直しで変わる）。`A) ` と `P) ` の行は、記号の後の空白1つで終わる：

S) 夜中に2回トイレで起き、あまり眠れなかった。朝食は半分で、食欲がない。

P)

## Glossary

- **NurseNote**: このアプリ全体（画面とバックエンド）。病棟の看護師がベッドサイドの会話から SOAP の S・O の下書きを根拠つきで作り、看護師が確かめて確定する
- **名簿API**: `GET /api/patients`。病棟の患者一覧を返す（live では Firestore の `patients` から読む。看護計画は Firestore に入れず、起動時の名簿の値を返す。要件2の9）
- **受け持ちAPI**: `PATCH /api/patients/{id}`。患者の受け持ちの看護師を変える（S-08）
- **下書きAPI**: `POST /api/drafts`。音声かテキストから下書きを作る。保存しない
- **照合API**: `POST /api/verify`。看護師が直した下書きの照合だけをやり直す。状態を持たない
- **確定API**: `POST /api/records`。看護師が確定した記録とタスクを保存し、カルテ用の文を返す
- **記録閲覧API**: `GET /api/records/{record_id}`。保存した記録の全体と、作り直したカルテ用の文を返す
- **カルテ文生成**: 確定した記録からカルテ用の文（`chart_text`）を作るバックエンドの処理（今は `backend/app/services/chart.py`）
- **確認画面**: 下書きを看護師が確かめ、直し、確定する画面（今は `frontend/js/screens/review.js`）
- **Gemini呼び出し**: Gemini に下書き作り（①）と二段目の確認（②）を頼むバックエンドの部分
- **操作記録**: Cloud Logging に出す構造化ログ。時刻と数だけを出す（P-04）
- **名簿seed**: `backend/seed/patients.json`。架空の病棟の患者一覧（今は6人）で、起動時に読む
- **起動時の名簿**: NurseNote が起動のときに名簿seed から1回読んでメモリに置いた患者の一覧（今のコードの `roster`）。下書きAPI・確定API・記録閲覧API は、患者と看護計画をここから引く
- **看護計画**: 患者ごとの看護上の問題と、それに対する計画（例 `#急性疼痛`）。`id`（例 `cp04`。名簿全体で重ならない番号）と `label`（例 `#急性疼痛`）を持つ。SOAP の P（計画。今の確認画面の見出しは「P　計画」）とは別のもの
- **`care_plans`**: 患者が持つ看護計画の並び。名簿API・下書きAPI・受け持ちAPI の出力の `patient` に入る
- **`plan_id`**: S・O の文に付ける、看護計画の `id`。`null` は計画外
- **計画外**: `plan_id` が `null` の S・O の文。どの看護計画にも当たらない文。カルテ用の文を作るときは、選んだ患者の `care_plans` にない `plan_id` の文も計画外として扱う（要件8の14）
- **看護計画の欄・計画外の欄**: 確認画面とカルテ用の文で、S・O の文を看護計画ごとにまとめた部分と、計画外の文をまとめた部分
- **S・O の文**: 下書きと記録の `soap.S`・`soap.O` の各要素（`text`・`evidence`・`added_by` を持つ）
- **確定する S・O の文**: 確定API に届いた S・O の文から、看護師が `decisions` で「消す」と決めた文を除いたもの
- **選んだ患者**: 看護師が名簿から選び、`patient_id` で送る患者（S-01）
- **場面**: モックの見本の会話と下書きの組（今は s1〜s5）。`backend/mock/source/scenarios.json` で患者に結びつく（s1 は p302、s2 は p305、s3 は p308、s4 は p310、s5 は p312）。場面のない患者（今は p303）には場面 s1 を返す
- **見本の下書き**: `mode` が `mock` のときに下書きAPI が返す、場面ごとの下書き（`backend/mock/draft_*.json`）
- **二段目の確認**: 各文が根拠の発言だけから言えるかを Gemini に判定させる確認（A-04）
- **署名（`entail_seals`）**: 二段目の判定1件ごとのサーバーの署名。文・根拠の発言・判定に結びつき、場所（`soap.S[0]` など）で照らし合わせる（A-04・A-05）
- **`draft_token`**: AI が書いた要素の指紋へのサーバーの署名（A-12）
- **看護師が足した要素**: `added_by` が `nurse` の要素（A-12）
- **`unknown_care_plan`**: 確定API が、選んだ患者の看護計画にない `plan_id` を受け取ったときに返す `422` の `error.code`（R-03）
- **id の形**: 英数字・`_`・`-` の1〜40字（`backend/app/models/limits.py` の `SafeId`）

## Requirements

### Requirement 1: 患者ごとの看護計画を名簿に持たせる

**User Story:** 病棟の看護師として、名簿の患者ごとに看護計画が入っていてほしい。確認画面で、文をどの看護計画に付けるかを選べるようにするため。

**関わる決まり:** P-07、S-08、SEC-04

#### Acceptance Criteria

1. THE 名簿seed SHALL すべての患者に `care_plans` を持たせ、各看護計画には `id` と `label` の2つの欄だけを入れる。看護計画のない患者には空の配列を入れ、`care_plans` の欄を省かない
2. THE 名簿seed SHALL p305（305号室 佐藤 和夫さん）の `care_plans` に、`id` が `cp04`、`label` が `#急性疼痛`（先頭は半角の `#`）の看護計画を1件入れる（新しい台本は live のデモで使う。決定6）
3. THE 名簿seed SHALL 6人全員の `care_plans` に、その患者の場面の会話に合う架空の看護計画を1件以上入れる（場面のない p303 は、下書きAPI が返す場面 s1 の会話に合わせる）。どの計画にするかと、p305 に `cp04` のほかの看護計画を足すか（場面 s2 の会話は `#急性疼痛` に当たらない）は、要件10の2を満たすように design で決める（決定6）
4. THE 名簿seed SHALL 看護計画の `id` を id の形にし、名簿全体（すべての患者の看護計画）で同じ `id` を2つ以上入れない（文字列が完全に同じものを重なりとみなす。ほかの患者の計画の `id` が選んだ患者の計画と同じだと、R-03 の確定のときの確かめで見つけられないため）。`id` には看護計画の中身を表す言葉を入れず、`cp` と2桁の通し番号（例 `cp01`）にする（記録に `label` を残さない決定2 を、`id` からも崩さないため。review-1 の指摘9）
5. THE 名簿seed SHALL 1人の患者の看護計画を0件から10件までにする（SEC-04。10件は仮置き。根拠になる測定はない）
6. THE 名簿seed SHALL 架空の看護計画だけを入れ、`label` に実在の患者・病院・看護師の名前を入れず、実在の患者の看護計画を写さない（P-07。確かめ方：提出前に、人が名簿seed のすべての `label` を見る）
7. THE 名簿seed SHALL 看護計画の `label` を次の条件に合わせる（SEC-04）。1字以上100字まで（全角・半角を問わず1文字を1字と数える。100字は仮置き）、改行を含めない、空白（半角・全角のスペース）だけにしない、1人の患者の中で同じ `label` を2つ以上入れない。確認画面の選択肢とカルテ用の文の見出しで、看護計画を見分けられるようにするため
8. THE 名簿seed SHALL 患者の人数（今は6人）、並び（部屋番号の順、S-08）、`care_plans` 以外の欄の値を、この機能を入れる前と同じにする
9. IF 起動のときに読んだ名簿seed の看護計画が、4 の `id` の形と名簿全体での重なり、5、7 の条件に1つでも合わない, THEN THE NurseNote SHALL `mode` が `mock` でも `live` でも起動を止め、看護計画が条件に合わないことを示すエラーをログに出す。今、名簿seed の形が合わないときに起動が止まるのと同じ扱いにし、条件に合わない名簿のまま API を受け付けない。`id`・`label` の文字列はログに出さない（要件9の4と同じ）。4 の `cp` と2桁の番号の形と、10 の条件は、起動のときには確かめず、名簿seed のテストで確かめる
10. THE 名簿seed SHALL 看護計画の `label` の前後に空白（半角・全角のスペース、タブ）を入れず、`label` を「計画外」にせず、1人の患者の中で、NFKC で正規化して前後の空白を除くと同じになる `label` を2つ以上入れない（例：「#急性疼痛」と「＃急性疼痛」）。確認画面の選択肢とカルテ用の文の見出しで、見た目の同じ看護計画や、計画外の欄と同じ見出しを出さないため（確かめ方：名簿seed のテスト。review-1 の指摘12）

### Requirement 2: 名簿と下書きの応答で看護計画を返す

**User Story:** 画面を作る Aさんとして、名簿と下書きの応答で、選んだ患者の看護計画を受け取りたい。確認画面に看護計画の選択肢を出すため。

**関わる決まり:** C-07、SEC-02、S-08

#### Acceptance Criteria

1. WHEN 名簿API が呼ばれる, THE 名簿API SHALL 各患者の `care_plans` を、名簿seed のその患者の看護計画と、件数・並び・各看護計画の `id` と `label` が1字も違わない形で返す（患者の並びは今のとおり部屋番号の順、S-08。live で、起動のときに名簿を Firestore に入れるのに失敗した場合は除く。「前提・制約」）
2. IF 起動時の名簿で、患者の `care_plans` の欄がないか、`null` か、空の配列である, THEN THE 名簿API SHALL その患者の `care_plans` を空の配列 `[]` で返す（欄を省かず、`null` にしない）
3. WHEN 下書きAPI が下書きを返す, THE 下書きAPI SHALL 出力の `patient` の `care_plans` に、入力の `patient_id` の患者について起動時の名簿にある `care_plans` と同じ値と並びを入れ、ほかの患者の看護計画を入れない（音声とテキストの入力、`mode` の `mock` と `live` のどれでも）
4. WHEN 同じ名簿seed で起動した `mock` と `live` の名簿API がそれぞれ呼ばれる, THE 名簿API SHALL 両方の応答で各患者に1字も違わない `care_plans` を返し、応答の `mode` に起動した方の値を入れる（不変の性質、C-07）
5. WHEN 受け持ちAPI が患者の受け持ちを変える, THE 受け持ちAPI SHALL 出力の `patient` の `care_plans` を、変える前に名簿API がその患者に返した値と並びのまま返す（不変の性質）
6. WHEN 受け持ちAPI が患者の受け持ちを変えた後に名簿API が呼ばれる, THE 名簿API SHALL すべての患者の `care_plans` を、変える前と同じ値と並びで返す（不変の性質）
7. IF 受け持ちAPI の入力に `care_plans` の欄がある, THEN THE 受け持ちAPI SHALL その欄だけを使わずに捨て、ほかの欄は今のとおり扱い、どの患者の看護計画も変えない（看護計画は名簿seed からだけ入る）
8. THE 確認画面 SHALL 看護計画の選択肢を、下書きAPI か名簿API の応答の `care_plans` からだけ作り、Firestore を直接読まず、画面のコードに看護計画の値を書き込まない（SEC-02）
9. WHILE `mode` が `live` である, THE NurseNote SHALL Firestore の `patients` に看護計画（`care_plans`）を書かず、Firestore から読んだ患者に `care_plans` の欄があってもその値を使わない。名簿API・受け持ちAPI・下書きAPI・確定API・記録閲覧API は、どれも起動時の名簿の `care_plans` を使う（受け持ち（`assigned_to`）は今のとおり Firestore に書き、画面で変えた値を起動のたびに残す。決定3。保存先に病状に関わる情報を増やさず、Firestore の値で読み込みが失敗する道を作らないため。review-1 の指摘4）

### Requirement 3: S・O の文に看護計画の印（`plan_id`）を付ける

**User Story:** 病棟の看護師として、S・O の文ごとに「どの看護計画の文か」の印を付けたい。文を動かさずに、看護計画ごとの記録にするため。

**関わる決まり:** A-02、A-04、A-12、SEC-04

#### Acceptance Criteria

1. THE NurseNote SHALL 下書きAPI の出力と、照合API・確定API の入力の S・O の各文（看護師が足した文（`added_by: nurse`）も含む）に `plan_id` の欄を1つずつ持たせ、その値を、看護計画の `id` を表す id の形（英数字・`_`・`-` の1〜40字）の文字列か `null` のどちらかにする
2. IF 照合API か確定API に届いた S・O の文に `plan_id` の欄がない, THEN THE NurseNote SHALL `422` を返さず、その文を `plan_id` に `null` を送った文と同じに扱う（確定API はその文の `plan_id` を `null` として記録に残す。今の画面が `plan_id` を送らなくても動くように）
3. IF 照合API か確定API に届いた S・O の文の `plan_id` が、`null` でも id の形（英数字・`_`・`-` の1〜40字）の文字列でもない（空の文字列、41字以上、英数字・`_`・`-` 以外の文字を含む、数・配列・オブジェクトなど）, THEN THE NurseNote SHALL `422` を返し、`error.code` を `invalid_request` に、`error.message` を「どの文の `plan_id` が誤りか」を示す日本語（送られた値は含めない）にし、`mode` を入れる（照合API が確かめるのは形だけ。選んだ患者の看護計画にあるかは、確定API だけが確かめる。要件6）
4. THE NurseNote SHALL S・O の文を `plan_id` の値によらず、届いた `soap.S`・`soap.O` の同じ場所（同じ番号）に置いたまま扱い、`plan_id` で並べ替えず、別の配列へ移さない（照合API が返す `checks`・`entail_seals` の `path`（`soap.S[0]` など）が、`plan_id` を付ける前と同じ文を指すように。A-04・A-12）
5. THE NurseNote SHALL 下書きAPI・照合API・確定API と記録で、`soap.A`・`soap.P` を今のとおりそれぞれ1つの文字列の欄にする（看護計画ごとの A・P は持たない。下書きAPI は今のとおり A・P を空の文字列で返す。A-02）
6. IF 照合API か確定API が `plan_id` の形の誤りで `422` を返す, THEN THE NurseNote SHALL 記録とタスクを保存せず、その要求では Gemini呼び出し（下書き作り・二段目の確認）を1回もしない
7. WHEN 確定API が記録を保存する, THE 確定API SHALL 記録の `soap.S`・`soap.O` に、届いた下書きの文を元の順のまま残し、そこから除くのは看護師が「消す」と決めた文だけにし、`plan_id` の値で並べ替えない（消した文より後ろの文の番号が詰まるのは今のとおり）
8. IF 照合API か確定API に届いた、S・O の文以外の要素（バイタル・依頼・手で入力が必要なもの・医師への確認）に `plan_id` の欄がある, THEN THE NurseNote SHALL `422` を返さずにその欄を捨て、記録とタスクに残さない（印は S・O の文だけに付ける）

### Requirement 4: 文に看護計画を付けるのは看護師（AI は付けない）

**User Story:** 病棟の看護師として、文をどの看護計画に付けるかは自分で決めたい。計画への仕分けは看護の判断で、選んだ患者の情報を AI に渡さないため。

**関わる決まり:** A-09、A-01、新しい決まり A-14（11/18 決定）

#### Acceptance Criteria

1. WHEN 下書きAPI が下書きを返す, THE 下書きAPI SHALL S・O のすべての文の `plan_id` を、欄を省かずに `null` で返す（`mode` が `mock` でも `live` でも、入力が音声でもテキストでも、選んだ患者の `care_plans` が0件でも1件以上でも、Gemini の出力の中身によらない。A-14）
2. WHEN 下書きAPI が下書き作り（①）を呼ぶ, THE Gemini呼び出し SHALL Gemini に送る内容を、今のとおり発言の列、決まった指示文、Gemini に返させる下書きの形だけにし（指示文と形はこの機能の前と同じ）、看護計画の `id`・`label` を入れない（選んだ患者の計画も、ほかの患者の計画も入れない。「入れない」とは、発言の文か、看護師が書いた・直した文にもともと含まれる場合を除き、Gemini に送る内容のどこにもその文字列が現れないこと。看護師が文に「#急性疼痛」と書いた場合、その文は今のとおり Gemini に届く。A-09。review-1 の指摘11）
3. WHILE `mode` が `mock` である, WHEN 下書きAPI が見本の下書き（今は s1〜s5 の5つ）のどれかを返す, THE 下書きAPI SHALL S・O のすべての文の `plan_id` を `null` で返す（見本のファイルに `plan_id` の欄がない場合も、`null` 以外の値が入っている場合も同じ）
4. WHEN 下書きAPI・照合API（`entail` が `true`）・確定API（署名で裏付けられない文の呼び直し）のどれかが二段目の確認（②）を呼ぶ, THE Gemini呼び出し SHALL Gemini に送る内容を、今のとおり判定する文、その根拠の発言と前の質問、決まった指示文だけにし、`plan_id` に看護計画の `id` が入った文があっても、看護計画の `id`・`label` を入れない（「入れない」の意味は2と同じ。看護師が書いた・直した文は、判定する文として今のとおりそのまま送るので、その文に含まれる文字列は除く。A-09）

### Requirement 5: 確認画面で文ごとに看護計画を選ぶ

**User Story:** 病棟の看護師として、確認画面で S・O の文ごとに看護計画を選び、どの計画にも当たらない文は「計画外」の欄でまとめて見たい。計画に関係する内容と、それ以外の必要な情報を分けて把握するため。

**関わる決まり:** A-01、A-03、A-04、A-05、A-12、SEC-04、R-01（11/18 に書き換えを決定）、新しい決まり A-14（11/18 決定）

#### Acceptance Criteria

1. WHILE 確認画面が下書きを出している, THE 確認画面 SHALL S・O の各文に看護計画の選択肢を1組ずつ出す。選択肢は、下書きAPI の応答の `patient` に入った `care_plans`（要件2の3）の各看護計画の `label` を並びのとおりに置き、その後に「計画外」を置く。その文の今の `plan_id` に当たる選択肢を選んだ状態で出す（1つの文で選べるのは1つだけ）
2. WHEN 確認画面が下書きを最初に出す, THE 確認画面 SHALL S・O のすべての文の `plan_id` を `null` にし、すべての文を「計画外」の欄に出す（下書きの文に `plan_id` の欄がないときも、`null` 以外の値が入っているときも同じ。AI が付けた看護計画を引き継がない、A-14。AI の A・P を引き継がない今の作りと同じ）
3. WHEN 看護師が文に看護計画を選ぶ, THE 確認画面 SHALL 照合API の応答を待たずに、その文の `plan_id` を選んだ看護計画の `id` にし、その文を元の欄から外して、その看護計画の欄に出す
4. WHEN 看護師が文に「計画外」を選ぶ, THE 確認画面 SHALL 照合API の応答を待たずに、その文の `plan_id` を `null` にし、その文を元の欄から外して「計画外」の欄に出す
5. IF 下書きAPI の応答で、選んだ患者の `care_plans` が空の配列か、`care_plans` の欄がない, THEN THE 確認画面 SHALL 各文の選択肢を「計画外」だけにし、看護計画の欄を出さずに「計画外」の欄だけを出す
6. THE 確認画面 SHALL 看護計画の選択肢の名前を「看護計画」、看護計画の欄の見出しをその看護計画の `label`（例 `#急性疼痛`）、計画外の欄の見出しを「計画外」にし、SOAP の P の欄の見出しは今のまま「P　計画」にする（看護計画と SOAP の P を見分けるため、看護計画の選択肢と欄の見出しに「計画」だけの言葉を使わない）
7. WHEN 看護師が文の看護計画だけを変える, THE 確認画面 SHALL その文の次のものを変える前のまま残す：`text`・`evidence`・`added_by`、`soap.S`・`soap.O` の中の番号（「S 1文目」などの表示と、検証結果の指摘が指す文）、その文で選んだ「残す／消す」
8. WHEN 看護師が文の看護計画だけを変える, THE 確認画面 SHALL 照合API を呼ばず（`entail: true` でも `entail: false` でも）、`entail_seals` を変えずに持ち、確定ボタンを押せるかどうかとその理由の表示（例「修正内容を再検証してください」）を変える前と同じにする（Gemini の呼び出しを増やさないため。照合の結果は `plan_id` で変わらない、要件7の1）
9. WHEN 看護師が S・O の文を足す（A-12）, THE 確認画面 SHALL 足した文の `plan_id` を `null` にして「計画外」の欄に出し、AI の文と同じ看護計画の選択肢を出す
10. THE 確認画面 SHALL 看護計画の選択を、確定API を呼ぶまで画面を開いている間のメモリにだけ持ち、サーバーにもブラウザの保存領域にも保存しない（A-01。照合API は状態を持たないので、照合API に送る下書きに `plan_id` が入るのはよい）
11. WHEN 看護師が確定ボタンを押す, THE 確認画面 SHALL S・O の各文の `plan_id`（看護計画の `id` か `null`）を、`soap.S`・`soap.O` の同じ番号の文に入れて確定API に送る（看護計画を選んでいない文は `null`。すべての文が計画外でも今のとおり確定でき、看護計画の選択を確定の条件にしない）。削除予定の文（「消す」を選んだ文）の `plan_id` は、送る前に `null` に戻す（記録に残らない文なので失うものはない。名簿seed が変わった後に、選び直せない削除予定の文で `unknown_care_plan` にならないため。review-2 の指摘6）
12. WHILE 確認画面が下書きを出している, THE 確認画面 SHALL S・O の文を看護計画の欄と「計画外」の欄に分けて出す。看護計画の欄は `care_plans` の並びで出し、「計画外」の欄はその後に置く。各欄の中では S の文を先、O の文を後にし、それぞれ `soap.S`・`soap.O` の元の並びで出す。A・P の欄は今のとおり1つずつ、すべての欄の後に出す（カルテ用の文の順と同じ、要件8。文が1つもない欄も見出しだけは出す：画面の案。カルテ用の文と違い、どの看護計画があるかを見せるため。画面の形は design で確かめる）
13. WHILE 確定API の保存中か、保存結果が未確認（「再送」を待っている）である, THE 確認画面 SHALL 看護計画の選択肢を選べなくし、再送では最初の送信と同じ `plan_id` を送る
14. IF 確定API が `unknown_care_plan`（要件6の2）を返す, THEN THE 確認画面 SHALL 返った `error.message` を今の確定の失敗と同じ場所に出し、選んだ看護計画・直した文・「残す／消す」の選択を消さずに残し、看護計画を選び直して確定し直せるようにする
15. WHEN 看護師が S・O の文を「文を分ける」で分ける, THE 確認画面 SHALL 元の文の `text` を看護師が直した前半にし、後半を新しい文として同じ欄（`soap.S` か `soap.O`）の最後に足す。新しい文の `added_by` と `evidence` は元の文と同じ値にし（AI の文から分けたら `"ai"`）、`plan_id` は `null` にする（決定7）
16. WHEN 看護師が文を分ける, THE 確認画面 SHALL 元の文と足した文を除く S・O の各文について、`soap.S`・`soap.O` の中の番号と、その文で選んだ「残す／消す」を変えない（途中に差し込むと、後ろの文の場所（`soap.S[2]` など）がずれ、二段目の署名と「残す／消す」の `path` が別の文を指すため）
17. WHEN 看護師が文を分ける, THE 確認画面 SHALL 元の文の `plan_id` を分ける前のまま残す
18. IF 分ける文の欄（`soap.S` か `soap.O`）に文がすでに50（`models/limits.py` の `MAX_SENTENCES`）ある, THEN THE 確認画面 SHALL その欄の文を分けられなくする
19. WHEN 看護師が文を分ける, THE 確認画面 SHALL 分けた2文を、今の「文を直す」と同じく再検証が要る文として扱う（確定ボタンを押せるかどうかとその理由の表示（例「修正内容を再検証してください」）を、文を直したときと同じにする。分けた2文はどちらも下書きの文と違い、署名で裏付けられないため。A-04・A-05）
20. IF 分ける文が削除予定の文（看護師が「消す」を選んだ文）である, THEN THE 確認画面 SHALL その文を分けられなくする（分けると「消す」の決定が消え、看護師が消すと決めた中身が記録に残る道になるため。分けたいときは「消す」を外してから分ける。review-2 の指摘2）
21. WHEN 看護師が文を分ける, THE 確認画面 SHALL 看護師が文の中で指定した位置を分け目にし、その位置より前を前半、後ろを後半にする（分け目の指定の仕方と、分けるボタンの置き場所は、画面の担当の Aさんが決める。review-2 の指摘3）
22. IF 指定した分け目で、前半か後半のどちらかが空（空白（半角・全角のスペース、タブ、改行）だけの場合を含む）になる, THEN THE 確認画面 SHALL その位置では分けられなくし、文の数と `text` を変えない（空の AI の文が二段目に送られ、確定ボタンも止まらないため。review-2 の指摘3）
23. WHEN 看護師が分けた後半で「分けを戻す」を選ぶ, THE 確認画面 SHALL 後半を欄から取り除き、元の文（前半）の `text` を分ける前の文に戻す（分ける前に直していない AI の文なら、下書きの文と同じに戻るので、二段目の署名がまた合う）。確認画面は分けた後半を覚えておき、「分けを戻す」はその後半にだけ出す（分け目を間違えたときに、後半が AI の文として欄に残り続けないため。review-2 の指摘3）

### Requirement 6: 確定のときに看護計画を確かめ、記録に残す

**User Story:** 病棟の看護師として、確定した記録に文ごとの看護計画が残ってほしい。画面の作りに漏れがあっても、ほかの患者の計画や存在しない計画が記録に入らないようにするため（F だけで守らせない）。

**関わる決まり:** S-01、SEC-04、C-07、P-03、A-12、新しい決まり R-03（11/18 決定）

#### Acceptance Criteria

1. WHEN 確定API が下書きを受け取る, THE 確定API SHALL S・O のすべての文について、`plan_id` が `null` か、選んだ患者の `care_plans` にある `id` と1字も違わない（大文字と小文字も区別する）かを確かめる。確かめる文には、看護師が足した文と、`decisions` で消すと決めた文も含める（決定8）。照らし合わせる `care_plans` は、起動時の名簿にある選んだ患者の値（名簿seed の値）とする
2. IF id の形に合う `plan_id` が、選んだ患者の `care_plans` のどの `id` とも一致しない, THEN THE 確定API SHALL `422` を返し、`error.code` を `unknown_care_plan` に、`mode` を今の `mode` にする。`error.message` は、当たった文の場所（確認画面の文の表示と同じ「S 2文目」の書き方。番号は届いた下書きの `soap.S`・`soap.O` の番号。多いときは先頭の5つまでと、残りの数）を含み、看護計画を選び直すよう求める日本語の文（文言は design で決める）にし、看護計画の `label` と送られた `plan_id` の値を含めない（どの文を選び直せばよいかが画面で分かるように。review-1 の指摘8）。一致しない `id` には、ほかの患者の `care_plans` にある `id`（要件1の4 で、名簿全体で重ならない）、名簿のどの患者にもない `id`、選んだ患者の `care_plans` が空のときの `null` 以外の値を含める。id の形に合わない `plan_id` は、要件3の3のとおり `invalid_request` で扱う
3. IF 確定API が `unknown_care_plan` を返す, THEN THE 確定API SHALL 記録とタスクを保存しない。同じ `confirm_id` で前に保存した記録とタスクも書き換えない
4. WHEN 確定API が記録を保存する, THE 確定API SHALL 消さずに残した S・O の各文の `plan_id` を、送られた値のまま、その文と一緒に記録の `soap.S`・`soap.O` に残す。`null` の文と、届いたときに `plan_id` の欄がなかった文は、欄を省かずに `null` として残す
5. WHEN 確定API が、S・O のすべての文の `plan_id` が `null` の下書き（欄がない文を含む）を受け取る, THE 確定API SHALL 看護計画を選んでいないことを理由に確定を止めない。止める条件は、この機能の前と同じもの（`patient_not_confirmed`・`undecided_checks` の `409` など）だけにする。選んだ患者の `care_plans` が空のときも同じにする（看護計画の選択を確定の条件にしない）
6. WHEN 記録閲覧API が記録を返す, THE 記録閲覧API SHALL S・O の各文に、確定API が保存した `plan_id` を同じ値のまま入れて返す。確定の後に名簿の看護計画が変わっても、確かめ直さない
7. IF 保存した記録の文に `plan_id` の欄がない（この機能の前に確定した記録）, THEN THE 記録閲覧API SHALL その文の `plan_id` を `null` として返し、保存した記録は書き換えない
8. WHEN 確定API が下書きを受け取る, THE 確定API SHALL 1・2 の `plan_id` の確かめを、患者の確認（S-03。`409` の `patient_not_confirmed`）と、二段目の確認の呼び直しより先に行う（看護計画の確かめで止まる確定に、二段目の費用をかけないため。決定8）
9. IF 受け取った下書きが、`unknown_care_plan` の条件と `409` の条件（`patient_not_confirmed` か `undecided_checks`）の両方に当たる, THEN THE 確定API SHALL `422`（`unknown_care_plan`）を返す（決定8）
10. WHEN 確定API が `added_by` が `"ai"` で下書きにない S・O の文を受け取る, THE 確定API SHALL その文を今のとおり AI の要素として照合と二段目にかける（「文を分ける」で足した後半など。今のコードでこうなるので、バックエンドは変えない。決定7）

### Requirement 7: 看護計画を選んでも、照合・二段目・費用は変わらない

**User Story:** バックエンドの持ち主の Cさんとして、看護計画を選んでも照合と二段目の確認の結果が変わらず、Gemini の呼び出しが増えないようにしたい。費用を増やさず、A-04・A-05・A-12 の守りを崩さないため。

**関わる決まり:** A-04、A-05、A-12、C-04、P-02

#### Acceptance Criteria

1. WHEN 照合API が、同じ発言の列と同じ `entail` の値で、`plan_id` だけが違う2つの下書きを受け取る, THE 照合API SHALL 2つに同じ `checks`・`missing`・`entail_seals` を返す（不変の性質）。この要件で「`plan_id` だけが違う」とは、S・O の文の数・並び・`text`・`evidence`・`added_by` と、S・O 以外の欄がすべて同じで、各文の `plan_id` だけが「`null`」「欄なし」「id の形の値」のあいだで違うことをいう。照合API は患者を受け取らないので、看護計画にない `plan_id` でも止めない。`entail` が `true` のときは、Gemini の二段目の判定が2回とも同じ場合に限る
2. WHEN 確定API が、下書きAPI か照合API（`entail: true`）が最後に返した下書きから `plan_id` だけを変えた下書きを受け取り、あわせて同じ発言の列と、そのとき返った `entail_seals` を受け取る, THE 確定API SHALL 署名で裏付けられた二段目の判定をそのまま使い、確定のときに Gemini の二段目を0回呼び、1日の上限（C-04）に数える回数を増やさない（変えた `plan_id` は、`null` か選んだ患者の看護計画の `id`）
3. WHEN 確定API が、`plan_id` だけを変えた下書きと `draft_token` を受け取る, THE 確定API SHALL どの要素を AI の要素として照合と二段目にかけ、どの要素を看護師が足した要素として扱うかを、`plan_id` を変える前の下書きを送ったときと同じにする（A-12。`draft_token` がない・合わないときも、変える前と同じ扱いにする）
4. WHEN 確定API が、`plan_id` だけが違う2つの下書きをそれぞれ記録として保存する, THE 確定API SHALL 2つの記録の `evidence_utterances` に、同じ発言（番号・話者・文）を同じ順・同じ件数で入れる（P-02。看護計画のために保存する発言を増やさない）
5. WHILE `mode` が `live` である, THE NurseNote SHALL 1日の上限（C-04）に数える回数を、`care_plans` と `plan_id` によらず次の今の数え方のままにし、看護計画のために Gemini と Speech-to-Text の呼び出しを足さない
   - 下書きAPI：テキストで2回、音声で2回と文字起こしの区切りの数（55秒ごとに1つ、3分で4つ）
   - 照合API：`entail` が `true` で1回、`false` で0回
   - 確定API：署名で裏付けられない文があるときだけ1回、ないときは0回
   - 上限の値：全体 300回/日、同じ接続元 30回/日のまま（今の既定）
6. WHEN 確定API が、`plan_id` とほかの欄（`text`・`evidence` など）の両方を変えた下書きを受け取る, THE 確定API SHALL 二段目を呼び直す文の場所と数を、その下書きの `plan_id` だけを元の値に戻して送ったときと同じにする（`plan_id` の違いで、呼び直す文を増やさない）
7. IF 確定API が、要件6の2の確かめで `unknown_care_plan` を返す, THEN THE 確定API SHALL Gemini の二段目を呼ばず、1日の上限（C-04）に数える回数を増やさない（看護計画の確かめで止まる確定に費用をかけないため）
8. WHEN 確定API が、看護師が「文を分ける」で分けた S・O の文（直した前半と、同じ欄の最後に足した後半。要件5の15）を受け取る, THE 確定API SHALL 今の文を直したときと同じく、2文を署名で裏付けられない文として扱い、二段目にかける。二段目は裏付けのない文をまとめて1回で送る（`services/drafting.py` の `recheck_entail`）ので、呼ぶのは確定か再検証（照合API の `entail: true`）の1回につき1回で、分けた文の数によらず 5 の数え方のまま（A-04。この機能のために変えない。決定7）

### Requirement 8: カルテ用の文を看護計画ごとにまとめる

**User Story:** 病棟の看護師として、カルテ用の文が看護計画ごとにまとまり、計画外の文はその後にまとまってほしい。看護計画に対して書く記録の形で、電子カルテに貼るため。

**関わる決まり:** R-01（11/18 に書き換えを決定）、S-06、A-02、A-06

**注:** カルテ用の文の形（見出しの行、文のない欄と行を出さないこと、計画外の文も入れること）は 11/18 に Cさんが決めた（決定5）。看護師には確かめていない（「成果を後で確かめる方法」の①で聞く）。この要件で**看護計画の付いた文**は、`plan_id` がカルテ文生成に渡した選んだ患者の `care_plans` のどれかの `id` と一致する文をいい、**計画外の文**はそれ以外の文（`plan_id` が `null` の文、欄がない文、`care_plans` にない `plan_id` の文。14）をいう。

#### Acceptance Criteria

1. WHEN S・O の文の1つ以上で `plan_id` が `null` でない, THE カルテ文生成 SHALL `chart_text` を「先頭の行（患者・日時）→ バイタルの行 → 看護計画の欄 → 計画外の欄 → A) の行 → P) の行」の順にし、行と行を今と同じ改行1つ（`\n`）でつなぎ、空の行と、最後の行の後の改行を入れない（バイタルの行は今の R-01 のとおり。T・BP・P・R・SpO2 の順で、血糖は最後。バイタルが1つもなければ行を出さない）
2. WHEN S・O の文の1つ以上で `plan_id` が `null` でない, THE カルテ文生成 SHALL 看護計画の付いた文が1つ以上ある看護計画の欄だけを、選んだ患者の `care_plans` の並びの順に1つずつ出し、文が1つも付いていない看護計画は見出しの行も出さない（看護計画は1人10件まで。要件1の5。仮置き）
3. THE カルテ文生成 SHALL 看護計画の欄を、その看護計画の `label` だけの行（例 `#急性疼痛`。前後に文字を足さない）で始め、`plan_id` がその看護計画の `id` である S の文の S) の行、O の文の O) の行の順に続ける
4. WHEN S・O の文の1つ以上で `plan_id` が `null` でなく、計画外の文も1つ以上ある, THE カルテ文生成 SHALL 1 の順のとおり看護計画の欄の後に、「計画外」だけの行で始まる欄を1つ出し、計画外の S の文の S) の行、O の文の O) の行の順に続ける（計画外の文が1つもなければ「計画外」の行を出さない）
5. WHEN S・O の文の1つ以上で `plan_id` が `null` でない, THE カルテ文生成 SHALL 各欄の S) の行と O) の行を、その欄に文が1つ以上ある方だけ出す（例：O の文がない欄には O) の行を出さない）
6. THE カルテ文生成 SHALL S) の行と O) の行を、「S) 」か「O) 」（記号の後に空白1つ）の後に、その欄の文を `soap.S`・`soap.O` の元の並び（番号の小さい順）でつなげた形にし、つなぎ方を今と同じにする（文の前後の空白を除く。文と文の間に区切りの文字を入れない。今のカルテ文生成と同じ文の終わりの文字（「。」など）で終わらない文には「。」を足す）
7. WHEN S・O のどの文でも `plan_id` が `null` である（`plan_id` の欄がない文と、S・O に文が1つもない場合を含む）, THE カルテ文生成 SHALL 今の R-01 の形（先頭の行 → バイタルの行 → S) → O) → A) → P)。看護計画と計画外の見出しの行はない。S・O に文がなくても「S) 」「O) 」の行を出す）と1字も違わない `chart_text` を作る
8. THE カルテ文生成 SHALL 先頭の行を今のとおり「【{部屋}号室{ベッド} {氏名}様】{確定の日時}」の形にする（氏名はフルネーム、なければ名字。日時は日本時間の `YYYY-MM-DD HH:MM`。S-06）
9. THE カルテ文生成 SHALL 看護計画の欄と計画外の欄の後に、「A) 」の後に A をそのまま続けた行と、「P) 」の後に P をそのまま続けた行を、この順に1つずつ出し、A・P が空でも2つの行を出す（看護計画ごとの A・P は出さない。A-02）
10. THE カルテ文生成 SHALL S) の行と O) の行の「S) 」「O) 」の後ろに、前後の空白を除いた文の `text` と足した「。」のほかの文字を出さず、根拠のない文や看護師が足した文にも印（記号・言葉）を付けない（今のとおり。印は記録のデータにだけ残す。A-06）
11. THE カルテ文生成 SHALL 前後の空白を除いて1字以上ある S・O の各文を、`plan_id` の付け方によらず `chart_text` にちょうど1回ずつ出し、S の文は S) の行にだけ、O の文は O) の行にだけ出す（不変の性質：文が消えない・重ならない・S と O が入れ替わらない）
12. WHILE 起動時の名簿にある選んだ患者（部屋・ベッド・氏名・`care_plans`）が確定のときから変わっていない, WHEN 記録閲覧API が記録を返す, THE 記録閲覧API SHALL 確定API が確定のときに返した `chart_text` と1字も違わない `chart_text` を返す（往復の性質。今の画面 `frontend/js/app.js` は、2つが違うと「保存した記録と表示内容が一致しません。」で止まる）
13. IF S・O の文の `text` が前後の空白を除くと空である, THEN THE カルテ文生成 SHALL 今のとおりその文を出さず、1〜7 の条件（`plan_id` が `null` でない文があるか、欄や行に文が1つ以上あるか）を決めるときに、その文をないものとして扱う
14. IF 記録閲覧API が `chart_text` を作り直すときに、記録の文の `plan_id` が `null` でなく、起動時の名簿にある選んだ患者の `care_plans` にない（確定の後に名簿seed が変わって起動し直した場合や、患者が名簿にいない場合）, THEN THE 記録閲覧API SHALL エラーで止めずに記録を返し、その文を計画外の文として「計画外」の欄にちょうど1回出す（11 を守る。どの文も今の `care_plans` に当たらないときは、看護計画の欄がなく「計画外」の欄だけになる。決定2）
15. WHEN カルテ文生成が次の記録から `chart_text` を作る：選んだ患者が p305（305号室A 佐藤 和夫）、確定の日時が 2026-11-19 10:00（日本時間）、バイタルが体温 `37.2`・血圧 `132/84`・脈拍 `88`、`soap.S` が順に「起き上がるときに術創がズキッとする。痛みは10段階で4。」（`plan_id` は `cp04`）・「夜中に2回トイレで起き、あまり眠れなかった」（`null`）・「朝食は半分で、食欲がない。」（`null`）、`soap.O` が空、A・P が空, THE カルテ文生成 SHALL Introduction の「台本の場面と、期待する仕分け」の例と1字も違わない8行の `chart_text` を作る（A) と P) の行は「A) 」「P) 」で、記号の後の空白1つで終わる。p305 の `care_plans` に `cp04` のほかの看護計画があっても、文が付かないので 2 のとおり出ない）

### Requirement 9: 看護計画をログに出さず、数で追う

**User Story:** Cさんとして、看護計画（病状に関わる情報）をログに出さずに、計画の選ばれ方を数で追いたい。P-04 を守りながら、成果を確かめるため。

**関わる決まり:** P-02、P-03、P-04、P-07

#### Acceptance Criteria

1. WHEN 確定API が記録を保存する, THE 操作記録 SHALL 確定のログ（`record_confirmed`）の今の項目（時刻・照合の色・数）を変えずに、確定する S・O の文（看護師が消した文を除き、看護師が足した文を含む）のうち、看護計画が付いた文の数と計画外の文の数を、S と O に分けて0以上の整数で出す（0 でも省かない。`plan_id` の欄がない文は計画外として数える、要件3の2）
2. WHEN 確定API が記録を保存する, THE 操作記録 SHALL 確定のログに、文が付いた看護計画の数（確定する S・O の文のうち、前後の空白を除いて空でない文に出てくる、互いに違う `plan_id` の数。カルテ用の文に見出しが出る看護計画の数と同じになる（要件8の13）。0 から選んだ患者の看護計画の数まで。review-1 の指摘10）と、選んだ患者の看護計画の数（`care_plans` の件数）を、0 でも省かずに出す
3. WHEN 確定API が記録を保存する, THE 操作記録 SHALL 確定のログの S について「看護計画が付いた文の数 ＋ 計画外の文の数」を同じログの S の文の数と等しくし、O についても同じにする（不変の性質）
4. THE 操作記録 SHALL どの event の行にも、看護計画の `id`（例 `cp04`）、`label` の文字列（例 `#急性疼痛`。`#` を除いた `急性疼痛` も）、確定API に送られてきた `plan_id` の値を出さない（P-04。看護計画について出すのは数だけ）
5. IF 確定API が `unknown_care_plan` で止める, THEN THE 操作記録 SHALL その1回の確定につき1行を出し、event・severity のほかには、code（`unknown_care_plan`）と、選んだ患者の看護計画にない `plan_id` を持つ S・O の文の数（1以上の整数）だけを入れる
6. IF 確定API が `unknown_care_plan` で止める, THEN THE 操作記録 SHALL その確定について確定のログ（`record_confirmed`）を出さない（保存しなかった確定を、確定の数に入れないため）
7. THE 確定API SHALL 看護計画について、記録には S・O の各文の `plan_id` だけを残し、看護計画の `label` と `care_plans` の写しを記録とタスクに保存しない（P-03・P-04。保存先に病状の情報を増やさない。記録閲覧API は起動時の名簿からカルテ用の文を作り直す、要件8の12・14。決定2。名簿の `patients` にも書かない、要件2の9）

### Requirement 10: モックで看護計画の選択を試せる

**User Story:** 画面を作る Aさんとして、モックで看護計画の選択とカルテ用の文を確かめたい。バックエンドの live を待たずに画面を作るため。

**関わる決まり:** C-05、C-07、P-07

#### Acceptance Criteria

1. WHILE `mode` が `mock` である, WHEN 確定API が下書きを受け取る, THE 確定API SHALL `plan_id` の確かめ（要件6の1〜5）と看護計画ごとの `chart_text`（要件8）を `live` と同じ処理で作り、同じ患者・同じ下書き（`plan_id` を含む）・同じ確定の時刻に対して、`live` と1字も違わない `chart_text` を、`mode` を `mock` にした応答で返す（C-07）
2. WHILE `mode` が `mock` である, WHEN 下書きAPI が、S・O の文が1つ以上ある見本の下書き（今は場面 s1・s2・s3・s5）を返す, THE 下書きAPI SHALL その見本の下書きに、選んだ患者の `care_plans` のどれかの看護計画に付けられる S・O の文を1つ以上含める（見本の下書きは作り直さず、名簿seed の看護計画を見本の会話に合わせて選ぶ。決定6。場面のない p303 には場面 s1 が返る。どの文をどの看護計画に付けられるとみなすかは、design で場面ごとの期待として書く。場面 s4（p310）の見本の下書きには S・O の文がないので、この条件の外になる）
3. WHILE `mode` が `mock` である, IF 確定API が受け取った S・O の文の `plan_id` が選んだ患者の看護計画にない, THEN THE 確定API SHALL `live` と同じく `422`（`error.code` は `unknown_care_plan`、`mode` は `mock`）を返し、記録とタスクを保存しない（その文を計画外に直して確定する扱いに切り替えない）
4. WHILE `mode` が `mock` である, THE NurseNote SHALL 看護計画の受け渡し（名簿API・下書きAPI）、`plan_id` の確かめ（確定API）、`chart_text` の作り（確定API・記録閲覧API）のどれでも、Gemini・Speech-to-Text・Firestore を1回も呼ばない
5. WHILE `mode` が `mock` である, THE 下書きAPI SHALL すべての場面の見本の下書き（`backend/mock/draft_*.json`）を、今のコードと見本の元データから `python -m scripts.build_mocks` で作り直したものと同じ内容で返す（署名 `entail_seals` と `draft_token` は除く。`plan_id`・`care_plans` を足したときや照合を直したときに作り直し忘れると、`test_mock_files.py` の `test_mock_file_is_up_to_date` が食い違いを見つける）

## 作らないこと

| 作らないこと | 理由 |
|---|---|
| AI（Gemini）による看護計画への自動の仕分け | 患者の看護計画を Gemini に渡す必要があり、A-09（選んだ患者の情報を Gemini に渡さない）とぶつかる。仕分けの質を確かめる時間もない。変えるなら、決まりの変更として人が決める |
| 看護計画ごとの A・P | A・P は看護師が書く欄で、今のまま記録に1つずつにする（A-02）。時間に入らない |
| 看護計画の登録・編集の画面 | 看護計画は名簿seed からだけ入る。本番は電子カルテから読む |
| 電子カルテとのつなぎ込み | ハッカソンの範囲外。資料に書く |
| 仮確定・確定のあとの修正 | 別の Spec にする |
| 依頼（タスク）・医師への確認・手で入力が必要なもの・バイタルへの看護計画の印 | 看護師の指摘は S の中身。印は S・O の文だけに付ける |
| 看護計画の選択を確定の条件にすること | 計画を持たない患者や、計画外だけの記録もある。選ばなくても確定できる |
| 看護計画で絞り込む記録・タスクの一覧 | 今回の指摘に含まれない。Firestore のインデックスも増やさない |
| 保存した記録の画面で、文を看護計画ごとに並べ替えて見せること | 時間に入らない。記録の画面のカルテ用の文は、看護計画ごとにまとまって出る |
| 確定のときの看護計画の写し（`label`）を記録に残すこと | 保存先に病状の情報（看護計画の名前）を増やさない（P-03・P-04）。記録には文ごとの `plan_id` だけを残し、記録閲覧API は起動時の名簿から作り直す。名簿が変わった後は、当たらない文を計画外の欄に出す（要件8の14。決定2） |
| Firestore の `patients` に看護計画を書くこと | どの API も起動時の名簿の `care_plans` を返すので、書いても読まれない。書くと、保存先に病状に関わる情報が増え、Firestore の値が条件に合わないときに読み込みが失敗する道ができる（要件2の9。決定3。review-1 の指摘4） |
| モックの場面2（305号室）の見本の作り直し | 時間に入らない。新しい台本は live のデモで使い、名簿seed の看護計画を今の見本の会話に合わせる（決定6）。作り直すと、見本の元データ・`build_mocks`・見本のテストの見直しも要る |
| 下書きの指示文（プロンプト）の変更 | Gemini の出力が変わり、live での確かめ（費用、Cさんの承認）と、ほかの場面の見直しが要る。1つの文に計画の話と計画外の話が混ざったときは、看護師が「文を分ける」操作で分ける（要件7の8。決定7） |

## 前提・制約

- 追加開発は 11/18 12:00〜11/24 23:59。Cさんは 11/18 22:00 以降と 11/19 終日だけ。決勝（Demo Day）は 11/27

- 看護計画は名簿の患者（`Patient`）に足すが、Firestore の `patients` には書かない。どの API も起動時の名簿の値を使う（決定3、要件2の9）。記録には文ごとの `plan_id` が増えるだけで、Firestore は形を決めずに保存できるので、移し替えの作業はない見込み

- 個人情報：看護計画は病状に関わる情報で、起動時の名簿（メモリ）に増える。Firestore の `patients` には書かない（要件2の9）。デモは架空の計画だけを使う（P-07）。ログには出さない（P-04）。記録には `plan_id`（中身の分からない番号、要件1の4）だけを残し、`label` は残さない（要件9の7）

## 決めたこと（11/18、Cさん）

前の版で「人に決めてもらうこと」に挙げていた項目と、要件の細部について、11/18 に Cさんが決めたこと。要件の中では「決定1」のように番号で指す。

1. **データの形**。名簿API・下書きAPI・受け持ちAPI の出力の `patient` に `care_plans: [{"id", "label"}]`（ない患者は `[]`）。S・O の文に `plan_id`（id の形の文字列か `null`。送られなければ `null`）。確定で、選んだ患者の計画にない id は `422`（`error.code` は `unknown_care_plan`）。反映：要件2・3・6
2. **記録に看護計画の写しを残さない**。記録には文ごとの `plan_id` だけを残す。記録閲覧API は、起動時の名簿の `care_plans` を使ってカルテ用の文を作り直す。名簿の今の `care_plans` にない `plan_id` の文は、エラーにせず「計画外」の欄に出す（文はちょうど1回出す）。前の版の要件9の「`label` を残す場所」の受け入れ条件はやめ、「確定API は看護計画の `label` を記録とタスクに保存しない」にした。反映：要件8の14、要件9の7、作らないこと（前の版の7）
3. **看護計画は `Patient` に足すが、Firestore の `patients` には書かない**。読むときは起動時の名簿の値を使う（Firestore から読んだ患者に `care_plans` の欄があっても使わない）。受け持ちは今のとおり Firestore に書く。反映：要件2の9、作らないこと、前提・制約（前の版の7）

4. **R-01 の書き換えと、新しい決まり A-14・R-03 を、前の版の案のとおり決定**。反映：「決まりとの関係」、要件4〜6・8の「関わる決まり」（前の版の1・2）
5. **カルテ用の文の形**。看護計画の欄の見出しは `label` だけの行、計画外の欄の見出しは「計画外」の行。文が1つもない看護計画の欄と、欄の中の文がない S)・O) の行は出さない。計画外の文もカルテ用の文に入れる。どの文にも `plan_id` がなければ今の形と1字も違わない。看護師には確かめていない。反映：要件8（前の版の3）
6. **モック**。305号室の見本（場面2）は作り直さない。名簿seed の6人全員に、それぞれの見本の会話に合う架空の看護計画を1件以上入れる（どの計画にするかは design で決める）。p305 には `{"id": "cp04", "label": "#急性疼痛"}` を入れる（新しい台本は live のデモで使う）。反映：要件1の2・3、要件10の2、作らないこと（前の版の5・6）

7. **1つの文に計画の話と計画外の話が混ざったとき**は、看護師が確認画面の「文を分ける」操作で分ける。1回目の設計レビューの指摘5 を受けて、11/18 に Cさんが案 (b) に決めた。画面の担当は Aさん（タスク 1j の一部）。下書きの指示文は今回変えない。反映：要件5の15〜5の23、要件6の10、要件7の8、作らないこと（前の版の4）
