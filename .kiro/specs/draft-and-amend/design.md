# 保存済みの看護記録を一覧から修正する設計案

2026-11-20、Bさんのレビューを反映して実装した。[要件](requirements.md) の「保存済みの記録を一覧から修正する」と、記録からタスクへの反映を扱う。実装と確認の結果は [作業手順](tasks.md) に記録する。

## 使う人から見た流れ

「会話記録」の一覧から記録を開き、「コピー」の上にある「編集」を押す。記録の入力欄を保存済みの値で開き、修正後に「変更を確認」から内容を見て「変更を保存」を押す。「取り消す」なら最後に保存された詳細を再表示する。成功後の「コピー」は修正済みのカルテ用文を使う。共有の合言葉でその記録を閲覧できる人に編集を認める。

- 編集できるのはバイタル、SOAP、看護計画の振り分け、依頼、手で入力する欄、医師への確認。記録番号、患者、最初の記録日時、保存期限、原文の根拠は読み取り専用にする。
- 編集中の内容は画面内に置く。途中で保存に失敗した場合は入力を保持する。取り消しや別の記録への移動で編集状態を破棄する。
- ほかの利用者が同じ記録やその依頼の分類などを先に変更していた場合は、編集中の内容を勝手にかぶせない。画面で理由を示し、入力を確認しながら最新の記録を開き直せるようにする。

## どう保存するか

既存の `POST /api/records` は、会話全文と下書きの確認に使うデータを受け取り、タスクを作る。保存後にはその情報が残っていないため、記録番号を指定する `PATCH /api/records/{record_id}` を追加する案とする。サーバーが既存の記録を読み、元の患者・日時・期限を保ったまま、変更できる欄にだけ訂正を適用する。初回の確定フローと、通信失敗時の同じ確定の再送は区別する。初回の再送で訂正済みの内容を戻さないこともテストする。

| 入口 | 入出力の案 |
|---|---|
| `GET /api/records/{record_id}` | 今の詳細に、開いた後に別の人が変更したかを確かめる版番号 `revision` と、選べる看護計画を追加する。版番号のない旧記録は 0 として扱う。看護計画は名簿から返し、記録に写さない。 |
| `PATCH /api/records/{record_id}` | 変更差分と版番号を受け取り、保存後の詳細を返す。期限切れ・不存在は `404`、編集中に別の更新があった場合は `409`、編集できない欄や別の記録のタスクを指定した場合は `422`。保存前の内容確認は画面で行う。 |

例として A 欄だけを訂正するときは、`{"revision": 0, "changes": {"soap": {"A": "看護師が訂正した内容"}}}` を送る。構造化した欄は編集可能な種類を型で限定し、変更していない欄を送らない。配列内の位置を使う欄は、同じ版であることを確かめた上で位置を解釈する。依頼には、すでに保存した `task_id` を使う。ブラウザから送られた患者情報、根拠発言の本文、別の記録のタスクIDは材料にしない。

記録の更新と必要なタスクの更新は、Firestore の同じトランザクションにまとめる。メモリでも同じ動きにする。タスク一覧から緊急度などを変更して記録に反映した場合も、同じ記録の版番号を進める。書き込みの直前に版と期限を確認する。

## 手動の訂正と元の発言をどう扱うか

保存済みの記録の訂正は、人が口頭やメールなどから新しく得た情報も入力できる。元の発言との整合性をチェックせず、情報源の入力も必須にしない。保存前の画面で、看護師が自分の入力を確認する。サーバーは、合言葉、記録番号と患者とのひも付け、版、期限、入力の型や上限、看護計画とタスクの所属を確認する。Gemini に訂正内容の判断を任せない。

- 本文や測定値を手動で修正・追記した項目は、人が編集したことを表示する。修正前の文章に付いていた発言や照合結果を、修正後の内容の根拠として表示しない。その項目だけが参照していた発言は保存対象から外す。文章や測定値に変更のない項目は、元の根拠と確認結果を保つ。分類や看護計画の変更だけで、元の発言とのひも付けを外さない（P-02、A-06）。
- この扱いは確定済み記録の編集に限る。AI が生成した下書きの新規確定では、現在の照合・二段目の確認と、出所を偽れない仕組みを維持する（A-04・A-05・A-12）。
- 依頼の追加・訂正も、患者からの依頼であることを看護師が確かめて記入する。元の録音以外で受けた依頼も記入できるよう、R-02 に手動訂正時の扱いを明記した。

## タスクへの反映

- 対応する依頼を直したら、そのタスクの文・緊急度・分類など変更した項目を更新し、今の担当と完了状態を残す。並べ替えで別のタスクに状態を移さない。
- 依頼の追加では新しいタスクを未完了で作り、削除では対応するタスクだけを一覧から外す。タスクが確認できない旧記録は、依頼欄の変更を保留し、理由を画面に出す案。依頼以外の欄は修正できる。別の記録や単独のタスクは検索して結び直さない。
- 依頼に変更がなければ、タスクを作り直さない。タスクが保存できなければ、記録側にも変更を残さない。

## ファイルと進め方

| 作業 | 最初に触る場所 | 確かめること |
|---|---|---|
| 同じ記録を更新する入口を作る | `backend/app/routes/records.py`、`app/models/record_views.py`、保存先の `base.py`・`memory.py`・`firestore_store.py` | まず A・P の訂正で、同じ番号で保存できること、期限切れや版違いで止まることを確かめる。 |
| 一覧から編集して保存する画面をつなぐ | `frontend/js/screens/record-detail.js`、新しい `record-edit.js`、`app.js`・`state.js`・`history.js`・`api.js` | 「コピー」の上から編集でき、取り消しで変更されず、保存後のコピーが最新になる。既存の確定前確認と表示部品を再利用する。 |
| ほかの入力欄とタスクに対応する | 新しい `backend/app/services/record_amend.py` を入口に、既存の入力モデルと記録・タスク生成の部品を再利用する | 元の発言にない内容も訂正できる。複数の依頼がある記録で、変更・追加・削除・並べ替えが正しいタスクだけに反映される。片方だけの書き込みや、別の患者への付け替えはできない。 |

## 保存と費用

会話全文や音声、端末への途中保存は追加しない。操作ログには会話の文や患者名を載せず、件数と時刻を使う（P-04）。記録とタスクは既存の期限で消し、新しいインデックスや GCP の設定変更はこの案に含めない。

架空データの mock と Firestore の差し替えでテストする。手動訂正では Gemini と Speech-to-Text を呼ばない。クラウド上では、既存の記録と対応するタスクの読み書きが発生する。
